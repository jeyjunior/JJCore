JJCORE 2.3.0 - GENERATED KEYS, TYPE HANDLING, AND RAW SQL

Context
This release fixes the remaining defects found by the consumer test projects for SQLite, SQL Server, PostgreSQL, and MySQL that change behavior or add public API. Existing code keeps compiling, except in the rare cases listed under Compatibility. Read Behavior Changes before upgrading.

Fixes
- Generated keys: AddReturningAsync and AddAsync now read keys that the database generates without IDENTITY or AUTO_INCREMENT.
  - SQL Server: Guid and string keys generated by a default, such as NEWID(), are read with OUTPUT INSERTED ... INTO a table variable, which also works on tables with triggers. Before, SCOPE_IDENTITY() returned NULL and the call failed after the row had been inserted. Numeric keys still use SCOPE_IDENTITY().
  - SQLite: keys are read with INSERT ... RETURNING. Before, last_insert_rowid() returned the internal rowid, so a string key generated by a default returned 1, 2, and so on without any error. Requires SQLite 3.35 or later; the bundled SQLite is newer.
  - MySQL: MySQL can only return AUTO_INCREMENT values. A Guid or string key generated by a default or trigger now throws InvalidOperationException before the insert. Before, AddReturningAsync returned 0 or, on an open connection, the key of another row inserted earlier in the session, without any error. LAST_INSERT_ID() is reset before the insert, so a numeric key that does not come from AUTO_INCREMENT throws instead of returning another row's key.
  - When no key is returned, the message says that the row may already have been saved.
- SQLite: Guid properties could be written but not read, because Microsoft.Data.Sqlite stores Guid values as text. JJCore registers a Dapper type handler on the first SQLite operation, unless the application already registered a Guid handler. The handler reads Guid and text values only; Guid values stored as BLOB are not converted, because their byte order depends on the tool that wrote them.
- Transactions: commands that receive a transaction that was committed, rolled back, or ended by the server now throw InvalidOperationException before they run. On SQL Server, after an error with SET XACT_ABORT ON or a deadlock, SqlClient ran the following commands outside the transaction, so Rollback did not undo them.
- SQL Server: inserts and updates send DateTime values as datetime2. Before, SqlClient sent them as the legacy datetime type: values were rounded to 1/300 second even in datetime2 columns (10:00:00.123 was stored as 10:00:00.1233333), and dates before 1753 failed in the client.
- Mapping: properties with only a getter body, such as FullName => FirstName + " " + LastName, are no longer mapped as columns. Before, every insert and select of such an entity failed. Private setters, init setters, get-only auto-properties, and private setters declared in a base class are still mapped. [Column] keeps a computed property mapped.
- DateTimeOffset.MinValue is written as NULL, like DateTime.MinValue, and [RequiredField] rejects it. Before, it was written as 0001-01-01 or, on PostgreSQL, as -infinity.
- ToSql: CRLF and CR line breaks are handled like LF, and lines with only spaces are removed.

New API
- RawSql (JJCore.Domain.Models): wraps a condition or command that JJCore sends without translating bracketed identifiers. Use it for SQL that the translator does not handle, such as PostgreSQL ARRAY [name]. Overloads: DapperExtensions GetListAsync, GetByConditionAsync, and ExecuteQueryAsync, and the same methods in Repository<TEntity>.
- Repository<TEntity>.DeleteAsync(object id) and DeleteAsync(object id, IDbTransaction?, CancellationToken): delete by Guid, string, or any key type. The repository interfaces are unchanged until JJCore 3.0.
- GetListAsync(condition, cancellationToken), GetByConditionAsync(condition, cancellationToken), and ExecuteQueryAsync(query, cancellationToken) in DapperExtensions and Repository<TEntity>.
- JJCoreTypeHandlers.ReadDateTimeOffsetAsUtc(): optional. Reads DateTimeOffset properties from columns that return a DateTime without kind, such as MySQL datetime, as UTC instead of local time. It applies to every provider in the process. It does not fix MySQL timestamp columns, which the server converts using the session time zone.

Behavior Changes
- MySQL: AddAsync and AddReturningAsync with a Guid or string key generated by the database throw before the insert. Code that called AddAsync only to insert, ignoring the returned 0, must use [PrimaryKey(DatabaseGenerated = false)] with a key generated by the application, or AddBatchAsync.
- MySQL: a numeric key generated by a default or trigger throws after the insert instead of returning 0 or another row's key. LAST_INSERT_ID() of the session is 0 after such an insert.
- Transactions that are no longer usable throw InvalidOperationException from JJCore instead of the provider exception.
- SQL Server: DateTime values in inserts and updates are datetime2 parameters. Columns of type datetime, smalldatetime, and date are converted by the server, which rounds once instead of twice; values close to a rounding limit can be stored differently. For example, 23:59:59.9999999 in a date column was stored as the next day and is now stored as the same day, and 10:00:29.999 in a smalldatetime column was stored as 10:01 and is now stored as 10:00. Dates before 1753 in a datetime column are rejected by the server (error 242) instead of by the client. DateTime values stored in text or sql_variant columns are converted from datetime2, so their text format or base type changes.
- Computed properties without [Column] are no longer written. A computed property that maps to a real column, such as Slug => Title.ToLower(), needs [Column] to keep being written. A property with an explicit getter over a private field and no setter is also treated as computed.
- DateTimeOffset.MinValue is written as NULL and fails in NOT NULL columns.
- ToSql output changes for input with CRLF or CR line breaks and for lines with only spaces.
- SQLite: the Guid type handler is registered for the whole process on the first SQLite operation.

Compatibility
- Calls written as GetListAsync(default), GetByConditionAsync(default), or ExecuteQueryAsync(default), with the default literal as the first argument, become ambiguous between the string and RawSql overloads and no longer compile. Pass null or an empty string instead.
- Classes derived from Repository<TEntity> that already declare DeleteAsync(object, ...), GetListAsync(string, CancellationToken), GetByConditionAsync(string, CancellationToken), ExecuteQueryAsync(string, CancellationToken), or the RawSql overloads with the same signature receive warning CS0114, which fails the build with TreatWarningsAsErrors. Add override, or new, to those members.

Known Limitations
- Repository interfaces (IRepository<TEntity> and ICancellableRepository<TEntity>) do not declare the new overloads; they will be added in JJCore 3.0.
- PostgreSQL: bracketed text after a space, such as ARRAY [name] or dezenas [i], is still translated as an identifier. Use RawSql for these expressions.
- MySQL: DateTimeOffset values in datetime columns are still read as local time unless JJCoreTypeHandlers.ReadDateTimeOffsetAsUtc() is called.
- MySQL: deadlocks, DDL statements, and COMMIT inside procedures end the transaction without notifying MySqlConnector, so JJCore cannot reject the following commands. PostgreSQL turns COMMIT after a failed command into a rollback without an error. Roll back after any error inside a transaction.

Publication
All generated packages are written to artifacts/packages, which can also be used as a local NuGet source for validation.
Publish JJCore.Domain and JJCore.Infra.Data.Core before the provider packages. Publish JJCore.Infra.Data.PostgreSQL, JJCore.Infra.Data.SqlServer, JJCore.Infra.Data.SQLite, and JJCore.Infra.Data.MySQL before the aggregate JJCore.Infra.Data package.
